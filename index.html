01

מה זה גיט, ומה זה גיטהאב

פרק 1 מתוך 17
3 דקות קריאה

מקרה שימוש

הצוות עובד על דוח Power BI. שלושה אנשים שומרים גרסאות בשמות כמו "דוח_סופי_באמת_2". אחד דורס את השינויים של השני, ואף אחד לא יודע מה השתנה ומתי. כאן נכנסים גיט וגיטהאב.

מה צריך להבין

גיט (Git) הוא תוכנה שרצה על המחשב שלכם ושומרת היסטוריה של קבצים. כל שמירה נקראת קומיט (commit): תמונת מצב עם תיאור קצר ושם של מי שעשה אותה. אפשר לחזור לכל קומיט קודם.

גיטהאב (GitHub) הוא אתר שמחזיק עותק של ההיסטוריה הזאת בענן, ומוסיף מעליה עבודת צוות: סקירת שינויים, משימות, אוטומציה ופרסום אתרים. גיט הוא הכלי, וגיטהאב הוא המקום שבו משתפים אותו.

ריפו (repository) הוא תיקייה אחת עם כל הקבצים של פרויקט ועם כל ההיסטוריה שלהם.

צעד אחר צעד

  1. ככה נראה המסלול של שינוי אחד, מההתחלה ועד הסוף. שימו לב אליו, כי כל הפרקים הבאים הם צעדים בתוכו:
  2. יוצרים ענף (branch) - עותק עבודה מקביל שלא נוגע בגרסה הראשית.
  3. עורכים קבצים ושומרים קומיט.
  4. דוחפים (push) את הענף לגיטהאב ופותחים Pull Request - בקשה שאחרים יסתכלו על השינוי.
  5. מקבלים הערות, מתקנים, ומאשרים.
  6. ממזגים (merge) לגרסה הראשית. כולם רואים את השינוי, וההיסטוריה שמורה.

מה אמור לקרות

אין עדיין פלט להריץ. התוצאה של הפרק היא שאתם יכולים להסביר במשפט אחד מה ההבדל: גיט שומר היסטוריה במחשב, וגיטהאב מארח אותה ומוסיף שיתוף.

תרגיל

כתבו בשתי שורות איך אתם שומרים היום גרסאות של קובץ משותף, ואיזו בעיה אחת בשיטה הזאת גיט פותר.

02

חשבון ואבטחה ראשונית

פרק 2 מתוך 17
2 דקות קריאה

מקרה שימוש

נרשמים לגיטהאב בפעם הראשונה, ורוצים שחשבון העבודה לא ייפרץ בגלל סיסמה שדלפה.

מה צריך להבין

חשבון אישי דורש שם משתמש וכתובת מייל מאומתת. אפשר גם להירשם עם Google או Apple. שם המשתמש הופך לכתובת של הפרופיל והריפואים שלכם, אז בחרו שם שמתאים גם לעבודה.

גיטהאב ממליץ בחום להפעיל אימות דו-שלבי (2FA). השיטה המומלצת היא אפליקציית אימות (TOTP) והוספת מפתח אבטחה כגיבוי, ולא SMS. אפשר גם passkey שמחליף סיסמה.

בארגון עם חשבונות מנוהלים (Enterprise Managed Users) ההרשמה נעשית דרך הארגון, ולכן הצעדים כאן לא חלים עליו.

צעד אחר צעד

  1. נכנסים ל-github.com ולוחצים Sign up. מזינים מייל, סיסמה ושם משתמש, ומאמתים את המייל.
  2. פותחים Settings, ואז Password and authentication.
  3. בוחרים Enable two-factor authentication ובוחרים Authenticator app. סורקים את קוד ה-QR באפליקציית האימות, ומקלידים את הקוד שהיא מציגה.
  4. מורידים את קודי השחזור (recovery codes) ושומרים אותם במקום בטוח, מחוץ למחשב. אלה הדרך להיכנס אם הטלפון אבד.
  5. מוסיפים שיטה נוספת: passkey או מפתח אבטחה, כדי שלא תינעלו בחוץ.

מה אמור לקרות

בהגדרות החשבון מופיע שאימות דו-שלבי פעיל ("Enabled"), עם לפחות שתי שיטות שמורות: אפליקציה ושיטת גיבוי. בכניסה הבאה גיטהאב מבקש קוד לפני שהוא מכניס אתכם.

תרגיל

הפעילו 2FA בחשבון שלכם, שמרו את קודי השחזור, התנתקו והתחברו שוב כדי לוודא שהקוד עובד. אל תשתפו את קודי השחזור עם אף אחד.

להתקין גיט ולהגדיר שם

פרק 3 מתוך 17
2 דקות קריאה

מקרה שימוש

רוצים לשמור קומיט ראשון מהמחשב, אבל גיט עוד לא מותקן, והקומיטים צריכים להישמר על שמכם.

מה צריך להבין

גיט הוא תוכנה נפרדת שמתקינים על המחשב. אחרי ההתקנה מגדירים פעם אחת את שמכם ואת המייל שלכם, ואלה יופיעו על כל קומיט.

כתובת המייל בקומיט היא מה שמקשר אותו לחשבון בגיטהאב. אם אתם לא רוצים לחשוף מייל אמיתי, אפשר להשתמש בכתובת noreply ש-GitHub מספק בהגדרות המייל.

צעד אחר צעד

  1. מורידים ומתקינים Git מ-git-scm.com (Windows, Mac או Linux). ב-Windows מקבלים איתו גם Git Credential Manager.
  2. פותחים טרמינל (ב-Windows: Git Bash או PowerShell) ובודקים שהוא מותקן:
    git --version
  3. מגדירים שם ומייל. השם והמייל יישמרו על כל קומיט:
    git config --global user.name "השם שלכם"
git config --global user.email "you@example.com"
  4. בודקים מה נשמר:
    git config --global --list

מה אמור לקרות

הפקודה הראשונה מדפיסה גרסה, למשל git version 2.xx.x. הפקודה האחרונה מדפיסה שורות user.name=... ו-user.email=... עם הערכים שהקלדתם.

תרגיל

הגדירו שם ומייל, והריצו את פקודת הבדיקה. אם הופיעו שני הערכים, סיימתם.

  • שוכחים לסגור ולפתוח מחדש את הטרמינל אחרי ההתקנה, ואז git --version נכשל למרות שהכול הותקן.

  • מגדירים מייל שונה מזה של חשבון הגיטהאב, והקומיטים לא משויכים לפרופיל שלכם.

  • כותבים ערך עם רווח בלי מירכאות, וההגדרה נשמרת שגויה.

יצירת ריפו חדש בממשק האמיתי של GitHub.

מקרה שימוש

יש לכם פרויקט חדש, למשל פרויקט Power BI של המכירות. רוצים בית לקבצים שלו עם הסבר, ושלא יעלו אליו קבצים מיותרים.

מה צריך להבין

ריפו חדש נוצר בלחיצה. מוסיפים לו README (דף הבית של הפרויקט, מוצג אוטומטית), .gitignore (רשימת קבצים שגיט מתעלם מהם) ורישיון אם הפרויקט ציבורי.

חשוב: ריפו ציבורי נראה לכל העולם. ריפו פרטי נראה רק למי שהוזמן. נתוני הארגון והלקוחות שייכים לריפו פרטי.

צעד אחר צעד

  1. בפינה הימנית העליונה לוחצים על + ובוחרים New repository.
  2. בשדה Repository name מקלידים שם באנגלית, בלי רווחים, למשל sales-dashboard.
  3. בוחרים Visibility: Public או Private.
  4. מפעילים Add README. אפשר גם לבחור תבנית .gitignore מהרשימה.
  5. לוחצים Create repository.

מה אמור לקרות

נפתח דף הריפו: שם הריפו למעלה, רשימת קבצים (README.md) באמצע, ומתחתיה התוכן של ה-README מוצג כטקסט מעוצב. הכתובת היא github.com/שם-המשתמש/sales-dashboard.

תרגיל

גיט במחשב: init, add, commit

פרק 5 מתוך 17
2 דקות קריאה▶ כולל סרטון דמו

▶ הדגמה על הממשק האמיתי

פקודות git אמיתיות שהורצו בסביבת בדיקה (לא צילום מסך של מסך המשתמש).

מקרה שימוש

יש לכם תיקייה עם קבצי פרויקט ורוצים לשמור היסטוריה של שינויים, גם בלי חיבור לגיטהאב.

מה צריך להבין

בגיט יש שלושה מקומות: תיקיית העבודה (הקבצים שאתם עורכים), Staging (מה שבחרתם לשמור עכשיו) והיסטוריה (הקומיטים). git add מעביר ל-Staging, ו-git commit שומר מה שב-Staging כקומיט.

הפקודה הכי שימושית היא git status: היא אומרת מה השתנה ומה מחכה לשמירה. הריצו אותה לפני כל פעולה.

צעד אחר צעד

  1. יוצרים תיקייה ומאתחלים בה ריפו:
    mkdir demo && cd demo
git init
  2. יוצרים קובץ ובודקים מצב:
    echo "# Demo" > README.md
git status
  3. מוסיפים ל-Staging ושומרים קומיט עם הודעה:
    git add README.md
git commit -m "Add README"
  4. משנים את הקובץ, ובודקים מה השתנה לפני שמירה:
    echo "Second line" >> README.md
git diff
  5. שומרים קומיט שני ורואים את ההיסטוריה:
    git add .
git commit -m "Add second line"
git log --oneline

מה אמור לקרות

git status הראשון מציג את README.md תחת Untracked files. אחרי הקומיטים, git log --oneline מציג שתי שורות, כל אחת עם קוד קצר (hash) והודעה, והחדשה למעלה. git diff מציג את השורה שנוספה עם סימן +.

תרגיל

צרו תיקייה עם שלושה קבצי טקסט, שמרו קומיט נפרד לכל קובץ עם הודעה ברורה, והריצו git log --oneline. אמורות להיות שלוש שורות.

בדקו את עצמכם

שינתם קובץ והרצתם git commit בלי git add. מה קורה?

איזו פקודה מראה מה בדיוק שונה בקבצים לפני שמירה?

מה כתוב בהודעת קומיט טובה?

⚠ שגיאות נפוצות

  • שוכחים git add לפני ה-commit, והקומיט יוצא בלי הקבצים שרציתם.

  • עושים קומיט אחד ענק בסוף היום. קומיטים קטנים עם הודעה ברורה קלים יותר לסקירה ולחזרה אחורה.

  • כותבים הודעות כמו "עדכון" או "תיקון". הודעה טובה אומרת מה השתנה ולמה.

לחבר את המחשב לגיטהאב: clone, push, pull

פרק 6 מתוך 17
2 דקות קריאה

מקרה שימוש

הריפו נמצא בגיטהאב, ואתם רוצים לעבוד עליו מהמחשב ולשלוח חזרה את השינויים. או להפך: יש לכם ריפו מקומי ורוצים לגבות אותו.

מה צריך להבין

clone מעתיק ריפו מגיטהאב למחשב, כולל כל ההיסטוריה. push שולח קומיטים מהמחשב לגיטהאב. pull מביא מהגיטהאב שינויים שאחרים שלחו.

כתובת הריפו בגיטהאב נקראת remote, והשם הרגיל שלה הוא origin.

ב-HTTPS גיטהאב לא מקבל את סיסמת החשבון. משתמשים בGit Credential Manager (מותקן עם Git ב-Windows) שמתחבר דרך הדפדפן, או ב-Personal Access Token. פרק 15 מסביר טוקנים.

צעד אחר צעד

  1. בדף הריפו לוחצים Code ומעתיקים את כתובת ה-HTTPS. מריצים בטרמינל:
    git clone https://github.com/USER/git-practice.git
cd git-practice
  2. עורכים קובץ ושומרים קומיט:
    echo "New line" >> README.md
git add .
git commit -m "Add line from my computer"
  3. שולחים לגיטהאב. בפעם הראשונה ייפתח חלון כניסה דרך הדפדפן:
    git push
  4. בפעם אחרת, אחרי ששותף שלח שינוי, מביאים אותו:
    git pull
  5. ריפו מקומי שנוצר עם git init, ואתם רוצים לחבר אותו לריפו ריק בגיטהאב:
    git remote add origin https://github.com/USER/REPO.git
git branch -M main
git push -u origin main

מה אמור לקרות

אחרי git push הטרמינל מציג שורות על העלאת אובייקטים וסיומת בסגנון main -> main. בדף הריפו באתר מופיע הקומיט החדש עם ההודעה שלכם. אחרי git pull ללא שינויים מופיע Already up to date.

תרגיל

שכפלו את git-practice ממחשב, הוסיפו קובץ, שלחו, וודאו באתר שהקובץ הגיע. אחר כך ערכו קובץ באתר והריצו git pull במחשב.

בדקו את עצמכם

ערכתם קובץ באתר גיטהאב. איך מקבלים אותו במחשב?

מה זה origin?

ה-push נכשל עם שגיאת הרשאה כשהקלדתם את סיסמת החשבון. למה?

⚠ שגיאות נפוצות

  • ה-push נדחה עם הודעת rejected כי מישהו דחף לפניכם. עושים pull, פותרים את ההבדלים ודוחפים שוב.

  • מנסים להתחבר בטרמינל עם סיסמת החשבון. גיטהאב דורש טוקן אישי (PAT) או מפתח SSH במקום סיסמה.

  • מחפשים את הקבצים במקום הישן: clone יוצר תיקייה חדשה, וצריך להיכנס אליה.

מקרה שימוש

צריך לשנות מדד מרכזי בדוח. אתם לא רוצים שהשינוי הלא גמור יגיע לדוח שהמנהלים רואים. פותחים ענף ועובדים בו.

מה צריך להבין

ענף (branch) הוא קו היסטוריה מקביל. הענף הראשי נקרא בדרך כלל main והוא הגרסה שסומכים עליה. כל שינוי נעשה בענף משלו ורק אחרי סקירה חוזר ל-main.

ענף לא מעתיק קבצים. הוא מצביע על קומיט, ולכן יצירה והחלפה בין ענפים מהירות.

שמות ענפים טובים מתארים את העבודה: fix-returns-measure או add-region-slicer.

צעד אחר צעד

  1. מוודאים שהענף הראשי מעודכן, ופותחים ענף חדש ועוברים אליו:
    git switch main
git pull
git switch -c fix-returns-measure
  2. עורכים קובץ ושומרים קומיט כרגיל:
    echo "Returns measure fixed" >> notes.md
git add .
git commit -m "Fix returns measure"
  3. בודקים באיזה ענף אתם ומה הרשימה:
    git branch
  4. שולחים את הענף לגיטהאב. הדגל -u קושר אותו לענף מרוחק, ובהמשך מספיק git push:
    git push -u origin fix-returns-measure
  5. חוזרים לראשי כדי לראות שהשינוי לא שם:
    git switch main

מה אמור לקרות

git branch מציג רשימת ענפים וכוכבית ליד הנוכחי. אחרי push, גיטהאב מציג בדף הריפו באנר צהוב "Compare & pull request" לענף החדש. אחרי ה-switch ל-main, הקובץ notes.md כבר לא מכיל את השורה החדשה.

תרגיל

פתחו ענף בשם add-notes בריפו git-practice, הוסיפו קובץ, שמרו קומיט ושלחו. בדקו באתר שהענף מופיע ברשימת הענפים, ושב-main אין את הקובץ.

  • נשארים על ענף ישן שבועות. מושכים מ-main מדי כמה ימים כדי שהקונפליקטים יישארו קטנים.

פתיחת Pull Request בממשק האמיתי.

מקרה שימוש

סיימתם לתקן מדד בענף. לפני שזה נכנס ל-main, חבר לצוות צריך לראות מה שונה ולאשר.

מה צריך להבין

Pull Request (PR) הוא בקשה למזג ענף לתוך ענף אחר, בדרך כלל main. הוא מציג את כל ההבדלים שורה אחר שורה, ומקום לדיון.

כותרת ותיאור טובים חוסכים שאלות: מה שונה, למה, ואיך בדקתם.

אפשר לפתוח Draft PR (טיוטה) כשהעבודה עוד לא מוכנה לסקירה.

צעד אחר צעד

  1. אחרי שדחפתם ענף, פותחים את דף הריפו באתר ולוחצים על הכפתור Compare & pull request.
  2. בודקים שהבסיס (base) הוא main ושההשוואה (compare) היא הענף שלכם.
  3. כותבים כותרת ותיאור. אפשר לציין Fixes #12 כדי לסגור משימה אוטומטית כשהכל ימוזג (פרק 10).
  4. בוחרים Reviewers ברשימה בצד ימין.
  5. לוחצים Create pull request. כדי לפתוח טיוטה, בוחרים בחץ ליד הכפתור את Create draft pull request.

מה אמור לקרות

נפתח דף ה-PR עם מספר (למשל #3), לשוניות Conversation, Commits, Files changed, וכפתור ירוק בתחתית שמסמן שאפשר למזג, אם אין קונפליקטים. בלשונית Files changed רואים שורות ירוקות שנוספו ואדומות שנמחקו.

תרגיל

פתחו PR מהענף add-notes אל main בריפו git-practice, כתבו תיאור בשלוש שורות: מה, למה, איך בדקתי. אל תמזגו עדיין.

בדקו את עצמכם

מה Pull Request עושה?

העבודה עוד באמצע, אבל רוצים שהצוות יראה כיוון. מה עושים?

איזו לשונית מציגה את השורות ששונו?

⚠ שגיאות נפוצות

  • פותחים PR לענף היעד הלא נכון. בודקים את שורת base ו-compare לפני היצירה.

  • פותחים PR ענק עם עשרות קבצים. PR קטן וממוקד מקבל סקירה מהירה וטובה יותר.

  • משאירים את התיאור ריק. כותבים מה השתנה, למה, ואיך בדקתם.

מיזוג ה-PR וסגירת ה-Issue אוטומטית.

מקרה שימוש

חבר לצוות סקר את ה-PR והעיר הערה. אחרי התיקון מאשרים וממזגים, ובמקרה שמישהו שינה את אותו קובץ בו-זמנית, פותרים קונפליקט.

מה צריך להבין

סוקר יכול לכתוב Comment, Approve או Request changes.

יש שלוש דרכי מיזוג: Merge commit שומר את כל הקומיטים ומוסיף נקודת מיזוג. Squash and merge מאחד את כל הקומיטים לאחד, והוא מתאים כשה-PR הוא שינוי לוגי אחד. Rebase and merge מוסיף את הקומיטים בקו ישר.

קונפליקט קורה כששני ענפים שינו אותן שורות. גיט לא מחליט במקומכם, והוא מסמן את המקום וממתין שתבחרו.

צעד אחר צעד

  1. הסוקר נכנס ללשונית Files changed, לוחץ על + ליד שורה וכותב הערה. בסוף לוחץ Review changes ובוחר Approve או Request changes.
  2. אתם מתקנים בענף עצמו. כל קומיט חדש שנדחף נכנס אוטומטית ל-PR:
    git add .
git commit -m "Address review comments"
git push
  3. כשהכל מאושר, לוחצים Merge pull request (או Squash and merge דרך החץ), ואז Confirm.
  4. אחרי המיזוג לוחצים Delete branch, ומעדכנים את המחשב:
    git switch main
git pull
  5. אם כתוב שיש קונפליקטים, מביאים את main לענף ופותרים:
    git switch my-branch
git merge main

מה אמור לקרות

כשהמיזוג מצליח ה-PR מקבל תג סגול Merged, ו-git pull ב-main מביא את הקומיט. בקונפליקט, גיט מדפיס CONFLICT (content): Merge conflict in notes.md, והקובץ מכיל סימנים: <<<<<<<, ======= ו->>>>>>>.

תרגיל

מזגו את ה-PR שפתחתם בפרק הקודם בשיטת Squash and merge, מחקו את הענף, והריצו git pull. אחר כך נסו ליצור קונפליקט בכוונה: שנו את אותה שורה בשני ענפים ומזגו.

פתיחת Issue בממשק האמיתי.

מקרה שימוש

בצוות יש רשימת תיקונים ורעיונות בוואטסאפ ובמיילים. מרכזים אותם במקום אחד עם אחראי, תוויות ותאריך.

מה צריך להבין

Issue הוא משימה, באג או שאלה שמנוהלת בתוך הריפו. לכל Issue יש מספר (#12), כותרת, תיאור ותגובות.

מוסיפים לו Labels (תוויות), Assignees (אחראים), Milestone (יעד) ואפשר גם לקשר אותו ל-Project.

קישור לקוד: אם התיאור של ה-PR כולל Fixes #12, מיזוג ה-PR סוגר את ה-Issue אוטומטית. המילים שעובדות הן closes, fixes ו-resolves וצורותיהן.

צעד אחר צעד

  1. בדף הריפו נכנסים ללשונית Issues ולוחצים New issue.
  2. כותבים כותרת, למשל "המדד Returns מחזיר ערך שלילי". בתיאור מפרטים מה ראיתם, מה ציפיתם, ואיך משחזרים.
  3. בצד ימין: בוחרים Assignee, Labels (bug) ו-Milestone.
  4. לוחצים Submit new issue. הוא מקבל מספר.
  5. כשפותחים PR שמתקן אותו, כותבים בתיאור:
    Fixes #1

מה אמור לקרות

הדף של ה-Issue מציג סטטוס Open, את התוויות והאחראי. אחרי מיזוג PR עם Fixes #1 ה-Issue עובר ל-Closed אוטומטית, ובציר הזמן מופיעה שורה שמציינת איזה PR סגר אותו.

תרגיל

פתחו ב-git-practice שני Issues עם תוויות, אחד מהם עם Assignee. אחר כך פתחו PR שמתקן את אחד מהם עם Fixes ומספר, ומזגו. ודאו שהוא נסגר.

איך סוגרים Issue אוטומטית כשמזגים PR?

מה תפקיד Labels?

מה כדאי לכתוב בתיאור של באג?

⚠ שגיאות נפוצות

  • כותבים "לא עובד" בלי פרטים. issue טוב כולל מה ניסיתם, מה קיבלתם, ומה ציפיתם שיקרה.

  • סוגרים issue בלי לקשר אותו ל-PR שפתר אותו. הקישור שומר את ההקשר למי שיגיע אחריכם.

  • פותחים issue כפול במקום לחפש קודם אם כבר קיים.

מקרה שימוש

יש 20 Issues פתוחים. המנהל רוצה לראות מה בתהליך, מה מחכה ומה הסתיים.

מה צריך להבין

Project הוא לוח מעקב שמתחבר ל-Issues ול-PRs. אפשר להציג אותו כBoard (עמודות לפי סטטוס, למשל Todo, In Progress ו-Done), Table או Roadmap.

צעד אחר צעד

  1. בעמוד הפרופיל או הארגון נכנסים ל-Projects ולוחצים New project.
  2. בוחרים Board (או Table או Roadmap), נותנים שם, ויוצרים.
  3. מוסיפים פריטים: לוחצים Add item, מקלידים # ובוחרים Issue מהריפו.
  4. גוררים כרטיסים בין העמודות. סטטוס הכרטיס הוא שדה שאפשר לשנות גם מתוך ה-Issue.

GitHub Actions: אוטומציה בתוך הריפו

פרק 13 מתוך 17
2 דקות קריאה▶ כולל סרטון דמו

▶ הדגמה על הממשק האמיתי

יצירת workflow והרצה ראשונה, בממשק האמיתי.

מקרה שימוש

בכל פעם שמישהו דוחף שינוי, רוצים שמשהו ייבדק לבד, למשל שקובץ מסוים קיים או שהפרויקט נבנה, בלי שמישהו יזכור להריץ.

מה צריך להבין

Actions היא מערכת אוטומציה של גיטהאב. מגדירים Workflow בקובץ YAML בתיקייה .github/workflows. הקובץ אומר מה מפעיל אותו (on), על איזה שרת הוא רץ (runs-on) ומה השלבים (steps).

ה-Workflow רץ על שרת ש-GitHub מספק. Actions חינמי בריפואים ציבוריים. בריפואים פרטיים יש מכסת דקות חינמית ומעבר לה יש חיוב, ולכן בדקו את התוכנית לפני שמפעילים הרבה.

אפשר להתחיל מתבנית מוכנה בלשונית Actions, ולהתאים אותה.

צעד אחר צעד

  1. בדף הריפו לוחצים Add file, ואז Create new file, ונותנים את השם .github/workflows/demo.yml.
  2. מדביקים:
    name: Demo
on: [push]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: echo "Branch is ${{ github.ref }}"
      - run: ls -la
  3. לוחצים Commit changes. הקומיט עצמו הוא push, ולכן ה-Workflow רץ.
  4. נכנסים ללשונית Actions, פותחים את הריצה האחרונה, ולוחצים על ה-Job כדי לראות את הלוג.

מה אמור לקרות

בלשונית Actions מופיעה ריצה עם סימן ירוק (הצלחה) או אדום (כישלון). בלוג רואים כל שלב, והשורה Branch is refs/heads/main ורשימת קבצי הריפו. אם יש שגיאה, השלב הכושל מסומן באדום וההודעה נמצאת בתוכו.

תרגיל

שנו את הקובץ כך שהשלב האחרון יהיה echo עם ההודעה "Hello from Actions", שמרו, וצפו בריצה החדשה. אחר כך שנו את הפקודה ל-exit 1 כדי לראות איך נראית ריצה שנכשלה, והחזירו.

בדקו את עצמכם

איפה חייבים לשמור קובץ Workflow כדי שגיטהאב יריץ אותו?

מה עושה השורה on: [push]?

מה עושים כשריצה נכשלת?

⚠ שגיאות נפוצות

  • כותבים סיסמה או מפתח ישירות בקובץ ה-yaml. סודות שומרים ב-Secrets ומשתמשים בהם עם ${{ secrets.NAME }}.

  • שמים את הקובץ במקום הלא נכון. הוא חייב לשבת בתיקייה .github/workflows ולהסתיים ב-.yml.

  • מניחים שהריצה נכשלה בגלל הקוד. פותחים את לוג הריצה וקוראים את השגיאה האדומה הראשונה.

אבטחה: טוקנים, סודות והגנה על main

פרק 15 מתוך 17
3 דקות קריאה▶ כולל סרטון דמו

▶ הדגמה על הממשק האמיתי

טופס Token (לא נשלח), Secrets ו-Rulesets: צפייה בלבד.

מקרה שימוש

מישהו הדביק בטעות מפתח גישה בקובץ ודחף אותו, או שמישהו דחף שינוי ישירות ל-main בלי שאף אחד ראה.

מה צריך להבין

Personal Access Token (PAT) הוא מפתח שמחליף סיסמה בסקריפטים ובכלים. גיטהאב ממליץ על Fine-grained tokens: בוחרים ריפואים מסוימים, הרשאות מינימליות ותפוגה. שמרו אותו כמו סיסמה, והוא מוצג פעם אחת בלבד.

סודות (Secrets) לא נכתבים בקוד. מוסיפים אותם בהגדרות הריפו ומשתמשים בהם ב-Workflows. גיטהאב לא מצנזר סוד שמודפס בלוג בדרכים עקיפות, לכן לא מדפיסים אותו.

Secret scanning סורק את כל ההיסטוריה בחיפוש סודות, והוא פועל כברירת מחדל בריפואים ציבוריים.

Rulesets מגדירים חוקים על ענפים, למשל לחייב Pull Request ואישור לפני מיזוג ל-main. כך אי אפשר לדחוף ישירות.

סוד שנחשף כבר נחשב דלוף. מבטלים (Revoke) אותו מיד ויוצרים חדש, ולא מסתפקים במחיקה מהקובץ.

צעד אחר צעד

  1. יצירת טוקן: תמונת הפרופיל, Settings, Developer settings, Personal access tokens, Fine-grained tokens, Generate new token.
  2. נותנים שם, בוחרים תפוגה קצרה, ב-Repository access בוחרים ריפואים מסוימים בלבד, ובהרשאות רק את הנדרש (למשל Contents: Read).
  3. לוחצים Generate token, ומעתיקים אותו מיד לכספת סיסמאות. אחרי שסוגרים את הדף לא רואים אותו שוב.
  4. סוד ל-Workflow: בריפו Settings, Secrets and variables, Actions, New repository secret. ב-Workflow מפנים אליו כך:
    env:
  API_KEY: ${{ secrets.API_KEY }}
  5. הגנה על main: ב-Settings של הריפו פותחים את Rules ואת Rulesets, יוצרים ruleset חדש שמכוון לענף main ומפעילים חוק שמחייב Pull Request לפני מיזוג. זמינות הפיצ׳ר בריפו פרטי תלויה בתוכנית, ולכן בדקו מה מוצג אצלכם.

מה אמור לקרות

בדף הטוקנים מופיע הטוקן שיצרתם עם תפוגה והרשאות. ב-Secrets מופיע שם הסוד בלי הערך. אחרי הפעלת ruleset, ניסיון push ישיר ל-main נדחה עם הודעה שהענף מוגן ושנדרש Pull Request.

תרגיל

צרו Fine-grained token לריפו git-practice בלבד, עם Contents: Read ותפוגה של 7 ימים, ומחקו אותו מיד אחרי שראיתם איך הוא נראה. אחר כך הוסיפו סוד בשם TEST_SECRET לריפו.

  • שומרים טוקן בתוך קוד או בקובץ בריפו. טוקן שדלף מבטלים מיד ומנפיקים חדש.

מקרה שימוש

שני אנליסטים משנים אותו מודל. עם קובץ pbix יחיד לא רואים מה השתנה ואי אפשר למזג. עם פרויקט PBIP, כל שינוי הוא שורות בקובץ טקסט שגיט מבין.

מה צריך להבין

ב-Power BI Desktop אפשר לשמור כPower BI Project (.pbip). במקום קובץ אחד נשמרות תיקיות של הדוח ושל המודל הסמנטי, והקבצים בהן הם טקסט קריא. זה בנוי כדי לעבוד עם גיט.

TMDL הוא פורמט טקסט שמתאר את המודל הסמנטי: טבלאות, עמודות ומדדים. מדד שנוסף הוא שורות חדשות בקובץ, ובקומיט רואים בדיוק מה השתנה.

לפי התיעוד של Microsoft, Power BI Desktop projects נמצא בתצוגה מקדימה (preview), והשילוב עם גיט מתואר דרך VS Code. כל פרטי התכונה עלולים להשתנות, ולכן כדאי לבדוק בתיעוד לפני שמחליטים על תהליך לארגון.

Power BI Desktop יוצר גם קובץ .gitignore שמתעלם מ-cache.abf ומ-.pbi/localSettings.json, שהם קבצים מקומיים.

ב-Fabric יש גם שילוב גיט ברמת סביבת העבודה (workspace) שתומך ב-GitHub. זה נושא נפרד מעבודת הקבצים כאן.

צעד אחר צעד

  1. ב-Power BI Desktop: File, Save as, ובוחרים סוג Power BI project (.pbip). התכונה בתצוגה מקדימה, ואם אינה מופיעה אצלכם, בדקו בתיעוד של Microsoft איך מפעילים אותה בגרסה שלכם.
  2. פותחים את תיקיית הפרויקט ב-VS Code ומאתחלים ריפו: Source Control, Initialize Repository. או בטרמינל:
    git init
git add .
git commit -m "Initial Power BI project"
  3. מחברים לריפו פרטי בגיטהאב ודוחפים (פרק 6):
    git remote add origin https://github.com/USER/sales-report.git
git branch -M main
git push -u origin main
  4. לכל שינוי פותחים ענף, ושומרים ב-Desktop. בקומיט רואים שורות שהשתנו בקבצי TMDL:
    git switch -c add-yoy-measure
git diff
  5. פותחים Pull Request וסוקרים את שורות ה-TMDL כמו כל קוד. ממזגים כשהסקירה הסתיימה.

מה אמור לקרות

בתיקייה יש SalesReport.pbip, תיקיית SalesReport.Report ותיקיית SalesReport.SemanticModel. אחרי הוספת מדד, git diff מציג בקובץ מתחת ל-definition קטע חדש שמתחיל ב-measure עם שם המדד וה-DAX שלו. ב-Pull Request אפשר לסקור את הקטע.

תרגיל

מה צריך להבין

כל שינוי, קטן או גדול, עובר אותה דרך. היא נשארת אותה דרך גם כשהפרויקט גדל.

צעד אחר צעד

  1. מתחילים מ-main מעודכן ופותחים ענף:
    git switch main
git pull
git switch -c short-description
  2. עורכים ושומרים קומיטים קטנים עם הודעות ברורות:
    git status
git add .
git commit -m "What changed and why"
  3. שולחים ופותחים Pull Request:
    git push -u origin short-description
  4. מגיבים להערות עם קומיטים נוספים לאותו ענף, ואחרי אישור ממזגים ומוחקים את הענף.
  5. חוזרים ל-main ומתעדכנים:
    git switch main
git pull

מה אמור לקרות

main מכיל את השינוי, ה-PR סגור (Merged), ה-Issue המקושר סגור, והענף נמחק. בהיסטוריה (git log --oneline) רואים קומיט עם ההודעה שלכם.

תרגיל

עברו על כל המסלול פעם אחת ב-git-practice: Issue, ענף, קומיט, Push, PR עם Fixes, מיזוג, ובדיקה שה-Issue נסגר. זה התרגיל המסכם.
